## §2 ユーザーフロー分析

- 主要ユースケースを **4W1H**（Who / What / When / Where / How）で整理する。
- ビジネス価値・技術難易度を軸に優先度マトリックスを作成する。
- 優先度の高いフローから集約候補・コンテキスト境界のヒントを読み取る。

## §3 ユビキタス言語確立

### 作成手順

1. **用語抽出** — 仕様書の名詞・動詞・状態を洗い出す。
2. **DDD 分類** — 以下の基準で分類する。

| 分類 | 判定基準 |
|------|----------|
| Entity | ID で識別・状態変化あり・ライフサイクル管理 |
| Value Object | 値そのものが識別子・不変・属性の組み合わせ |
| State / Action | システム状態・ユーザー操作・処理フロー |

3. **英語名決定** — UpperCamelCase、略語禁止、複合語は統一（例: AnswerHistory）。
4. **BDD 表現例作成** — Given（状態）/ When（操作）/ Then（結果）で表現する。

### Core Dictionary フォーマット

| 日本語 | 英語/変数名 (UpperCamelCase) | 定義 | BDD 表現例 |
|--------|------------------------------|------|------------|
| [日本語名] | [英語名] | [ドメイン定義] | [Given/When/Then 例] |

### 品質チェック

- 同じ概念に複数の表現が混在していない（一意性）
- UpperCamelCase で実装可能な英語名
- コード・文書・会話で同じ用語を使用

## §5 境界づけられたコンテキスト定義

### サイズ原則

- Bounded Context ≥ Aggregate
- Bounded Context ≤ Domain 全体
- 理想: 1 Context = 1 Team = 1 Microservice

### 境界設定基準

- **責務の独立性**: 変更が他コンテキストに波及しないか
- **用語の一意性**: 同じ用語が異なる意味を持たないか
- **変更の独立性**: デプロイ・スケールが独立できるか

### Conway's Law 考慮

チーム構造と context 境界を合わせることで摩擦を減らす。
1 チームが複数の core context を所有する場合はリスクを明示する。
