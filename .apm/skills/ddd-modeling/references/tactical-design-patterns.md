# 戦術的設計パターン詳細

## §1 ドメインオブジェクト分類

### 分類基準

| 分類 | 判定基準 | DB 表現 | 実装特徴 |
|------|----------|---------|----------|
| Entity | ID で識別・状態変化あり・ライフサイクルあり | テーブル化 | ID equality、lifecycle behavior、invariant check |
| Value Object | 値で識別・不変・属性の組み合わせ | フィールド化 | equality by value、immutable、replacement で更新 |
| Domain Service | 複数集約にまたがる計算・評価・調整 | なし | stateless、ドメイン言語で命名 |
| Aggregate | 整合性・トランザクション境界 | 集約ルートがテーブル | root が内部 entity/value の更新を制御 |

## §2 エンティティ関係分析

### 関係パターン

| パターン | 説明 | 実装方針 |
|----------|------|----------|
| 1対1 所有 | 一方が他方を完全に管理 | 同一集約内に含める |
| 1対多 所有 | 親が子の集合を管理 | 集約内コレクションまたは子集約ルート |
| 多対多 関連 | 双方向参照が必要 | 関連エンティティ（中間集約）を検討 |
| 参照関係 | ID 参照のみ | 他集約の ID のみ保持し直接参照しない |

## §4 集約設計

### 設計原則

- **整合性境界**: 集約内の不変条件は常に保証する
- **集約ルート経由**: 集約への操作は必ず集約ルートから行う
- **ID 参照**: 他集約は ID でのみ参照する
- **最小サイズ**: 不変条件が必要な範囲のみを含める

### 不変条件の記録（フォーマット）

| 集約名 | 不変条件 | 違反時の処理 | ビジネスルール根拠 |
|--------|----------|------------|------------------|
| [Aggregate名] | [条件] | [エラー/例外] | [仕様参照] |

### 2段階イベント発行パターン

1. **Phase 1 — トランザクション内イベント登録**: 集約メソッド内で `registerEvent(event)` を呼び、コミット前にキューに積む。
2. **Phase 2 — トランザクション成功後に発行**: Application Service がコミット後に `getUncommittedEvents()` を取得し、イベントバスへ発行する。

このパターンによりトランザクションの安全性とイベント駆動アーキテクチャを両立する。

### 集約設計テンプレート

|--------|-----------|----------------|--------------|------------|----------|
| [Aggregate名] | [ルート名] | [Entity リスト] | [VO リスト] | [Event リスト] | Strong/Eventual |

### Event Sourcing・CQRS・Saga の適用判断

| パターン | 適用場面 | 注意 |
|----------|----------|------|
| Event Sourcing | 監査証跡が必須・イベントから状態を再構築したい | スキーマ進化・スナップショット戦略が必要 |
| CQRS | 読み取りと書き込みのモデルが大きく異なる | プロジェクション管理コストが増える |
| Saga | 複数集約にまたがる長期トランザクション | 補償ロジックの設計が必要 |

## §5 ドメインイベント設計

### ドメインイベントの特性

- 過去形で命名する（例: `OrderPlaced`, `UserRegistered`）
- 発行元の集約・コンテキストが一意に決まる
- イベントペイロードにはコンテキスト横断に必要な最小限の情報を含める

### ドメインイベントカタログ（フォーマット）

| イベント名 | 発行集約 | 発火条件 | ペイロード | 購読者（下流） | 配信保証 | べき等性 |
|-----------|---------|----------|----------|--------------|---------|----------|
| [EventName] | [Aggregate名] | [条件] | [フィールド一覧] | [Context/Service] | At-least-once/Exactly-once | Required/Not Required |

### コンテキスト間連携パターン

| パターン | 使い分け |
|----------|----------|
| Synchronous API | 即時応答が必要・トランザクション境界を共有できる場合 |
| Event Publication | 疎結合・結果整合性で十分・スケーラビリティ重視 |
| Anti-Corruption Layer | 下流が上流モデルに汚染されないよう翻訳が必要 |
| Shared Kernel | 2 コンテキストが共有すべき小さな共通モデルがある場合 |

### 品質チェックリスト

- [ ] ユビキタス言語辞書の用語と一致している
- [ ] 不変条件がビジネスルールから導出されている
- [ ] 他集約への参照は ID のみ
- [ ] イベントのべき等性・配信保証が定義されている
- [ ] コンテキスト境界を越えるモデルに ACL/翻訳が設計されている
