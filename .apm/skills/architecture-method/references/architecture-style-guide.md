# アーキテクチャスタイル選定ガイド

## アーキテクチャスタイル比較

### システムアーキテクチャ

| アーキテクチャ | メリット | デメリット | 適用場面 | チーム規模 | 技術的複雑さ | 運用負荷 | 判定基準 |
|---------------|----------|------------|----------|------------|--------------|----------|----------|
| モノリス | 開発初期高速 / デプロイ単純 / トランザクション容易 / デバッグ容易 | 大規模時保守困難 / 技術スタック固定 / 部分スケール不可 | 小〜中規模 / MVP / 単一チーム | 1–10 名 | 低 | 低 | 小規模・スピード重視 |
| マイクロサービス | 独立デプロイ / 技術選択自由 / 障害分離 / チーム独立 | 分散複雑性 / データ整合性課題 / 運用コスト高 | 大規模 / 複数チーム / 高可用性 | 20 名以上 | 高 | 高 | 大規模・独立性重視 |
| モジュラーモノリス | モノリスの単純さ + モジュール分離 / 段階的移行可能 | 境界維持要努力 / 完全分離は困難 | 中規模 / 将来分割予定 / 成長期 | 5–15 名 | 中 | 中 | バランス重視 |

### アプリケーションアーキテクチャ

| パターン | 特徴 | 適用条件 | 注意点 |
|----------|------|----------|--------|
| レイヤードアーキテクチャ | 上位層が下位層に依存 / シンプル | CRUD 中心 / 小〜中規模 | ビジネスロジックが UI/DB に混入しやすい |
| ヘキサゴナルアーキテクチャ | ポート & アダプター / 外部依存を分離 | テスト容易性重視 / 外部連携多数 | ポート定義の設計コスト |
| クリーンアーキテクチャ | 依存関係逆転 / ドメイン中心 | 複雑ドメイン / 長期保守 | 初期設計コスト高 |
| オニオンアーキテクチャ | 同心円 / ドメインが核 | DDD と組み合わせる場合 | レイヤー増加で複雑化 |

## C4 モデル準拠の図作成指針

- **Level 1 (System Context)**: システムとユーザー・外部システムの関係、システム境界の明確化
- **Level 2 (Container)**: システム内のアプリケーション・データストア構成と通信方式
- **Level 3 (Component)**: 各コンテナ内のコンポーネント構成と責務分離

アーキテクチャフェーズでは Level 1–2 に留め、具体的なドメインエンティティ名・値オブジェクト名は DDD 設計フェーズで決定する。

## 通信方式選定マトリクス

| ユースケース | 推奨方式 | 理由 | 実装パターン |
|-------------|----------|------|-------------|
| リアルタイム応答必須 | 同期 (REST) | ユーザー待機 / 強一貫性 | Request-Response |
| バッチ処理 | 非同期 (Queue) | 長時間処理 | Fire-and-Forget |
| 複数システム連携 | 非同期 (Pub/Sub) | 結合度低減 | Event-Driven |
| データ同期 | 非同期 (Event) | 結果整合性許容 | Event Sourcing |

## 非機能要件チェックリスト

- [ ] **スケーラビリティ**: 水平 / 垂直スケーリング戦略を定義したか
- [ ] **可用性**: SLA 数値と冗長化方式 (Active-Active / Active-Standby) を決めたか
- [ ] **セキュリティ**: 認証 / 認可 / 暗号化 / 最小権限の原則を設計したか
- [ ] **性能**: 応答時間目標 (P95) とキャッシュ戦略を定義したか
- [ ] **障害対応**: Circuit Breaker / Bulkhead / Timeout を計画したか
