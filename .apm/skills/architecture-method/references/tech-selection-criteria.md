**判定凡例**: ○ 採用 / △ 条件付き検討 / × 不採用

## 選定必須カテゴリ

| カテゴリ | 選定が必要な理由 | 主要評価軸 |
|----------|----------------|------------|
| **データベース** | データ特性・一貫性要件に応じた選択 | ACID / BASE / スケール / 運用コスト |
| **ORM / クエリビルダー** | DB アクセスの統一と型安全性 | 型安全性 / パフォーマンス / マイグレーション機能 |
| **バリデーション** | API 入力検証と型システムとの統合 | 型推論 / エラーメッセージ品質 / エコシステム |
| **エラーハンドリング** | エラー伝播の一貫性確保 | 型安全性 / 学習コスト / 既存コードへの影響 |
| **HTTP クライアント** | 外部 API 連携の信頼性 | 機能性 / Bundle Size / TypeScript 対応 |
| **テストフレームワーク** | 開発サイクルの品質確保 | 実行速度 / TypeScript 対応 / エコシステム成熟度 |
| **デプロイ / インフラ** | 運用コストと可用性の両立 | 管理コスト / スケール / コスト |

## 評価軸の定義

### コスト
- **低**: 既存インフラ / OSS / 無料枠内で運用可能
- **中**: 中程度の費用、規模に応じて増加
- **高**: 高額ライセンス / 専門運用担当が必要

### 学習曲線
- **緩**: 既存チームスキルで即導入可能
- **中**: 1–2 週間程度の学習で習熟
- **急**: 数ヶ月の学習・訓練が必要

### チーム適合性
- **高**: チームの既存スキル / ツールと高い親和性
- **中**: 部分的に経験あり、追加学習で対応可能
- **低**: チームに経験者がほぼおらず、大きなリスク

## DB 設計評価基準

### 集約-テーブルマッピングパターン選択

| パターン | 適用条件 | 利点 | 欠点 |
|----------|----------|------|------|
| 1 集約 1 テーブル | シンプルな集約 | 単純 / 高性能 | 正規化不足になりやすい |
| 1 集約複数テーブル | 複雑な集約 | 正規化維持 | JOIN 必要 |
| 値オブジェクト埋め込み | 小さい値オブジェクト | シンプル | カラム数増加 |
| 値オブジェクト分離 | 大きい値オブジェクト | 正規化 | 結合必要 |

### 主キー設計

| ID タイプ | 利点 | 欠点 | 適用場面 |
|----------|------|------|----------|
| UUID | グローバル一意 / 分散対応 | サイズ大 / 性能劣化 | 分散システム / 外部連携 |
| Auto Increment | 高性能 / サイズ小 | 分散時衝突 / 推測可能 | 単一 DB / 内部用途 |
| ULID | 時系列順序 / 可読性 | 新しい技術 | 時系列重要 / 可読性必要 |

### インデックス作成判断基準

| 判断項目 | 作成する | 作成しない |
|----------|----------|------------|
| WHERE 頻度 | 高頻度 | 低頻度 |
| データ選択性 | 高選択性 | 低選択性 (例: bool) |
| 更新頻度 | 低更新 | 高更新 |

### データ一貫性戦略

- **ACID (強一貫性)**: 金融 / 決済 / 在庫など、整合性が絶対必要な場合
- **BASE (結果整合性)**: ソーシャル / コンテンツなど、遅延を許容できる場合
- **分散トランザクション**: 2 フェーズコミット (強一貫性) / Saga パターン (長時間 Tx / 補償処理可能)
