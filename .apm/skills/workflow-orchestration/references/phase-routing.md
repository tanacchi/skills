# フェーズ・ルーティング

## 標準工程マップ

| 工程 | 前提成果物 | 主な成果物 | 完了シグナル |
|------|-----------|-----------|-------------|
| 仕様整理 | なし（新機能の起点） | 要件・ユーザーストーリー・success/error シナリオ | 5W1H、acceptance criteria、open question が明確 |
| アーキテクチャ/技術選定 | 仕様整理の承認 | アーキテクチャ方針・技術選定比較・NFR | トレードオフと選定理由が文書化されている |
| ドメイン設計 (DDD) | アーキテクチャ承認 | ユビキタス言語・BC・エンティティ・VO・集約 | コンテキスト境界と不変条件がテスト可能な形で明確 |
| UI 設計 | ドメイン設計承認 | サイトマップ・フロー・ワイヤーフレーム・コンポーネント | DDD/API との整合性が確認されている |
| API 設計 | ドメイン設計承認 | API 仕様 (OpenAPI/TypeSpec 等)・エラー仕様 | スキーマファーストでコンテキストと揃っている |
| DB / データ設計 | API 設計承認 | データモデル・マイグレーション方針・制約 | 集約境界と永続化境界が対応付けられている |
| BDD テスト実装 | DB 設計承認 | Given-When-Then シナリオ・Step Definitions | 全シナリオが実装前に Red で失敗している |
| スケルトン実装 | BDD テスト承認 | コンパイル可能な骨格コード | BDD テストが依然として Red である |
| TDD テスト実装 | スケルトン承認 | 失敗する単体テスト・モック設計 | 全テストが Red で、カバレッジ設計が完了している |
| TDD 実装 (Red→Green) | TDD テスト承認 | プロダクションコード・リファクタリング済み実装 | 全単体テストが Green、カバレッジ目標達成 |
| BDD 統合テスト・実装完成 | TDD 実装承認 | 全 BDD テスト Green・完成した実装 | ビジネス仕様との整合性が確保されている |
| E2E テスト | BDD 統合テスト承認 | E2E シナリオ・実行結果 | 主要ユーザーフローの UI/API/DB flow が検証されている |

## 工程遷移ルール

### 通常フロー

各工程は上表の順序で進む。前工程の成果物と明示的なユーザー承認が必要。

### 前工程への差し戻し条件

- **要件不明確**: ビジネスルールが曖昧で実例検証が必要 → 仕様整理へ戻る
- **複雑なビジネスルール**: ドメインロジックが複雑で仕様検証が困難 → BDD へ戻る
- **技術制約の影響**: 選定技術の制約により要件調整が必要 → アーキテクチャへ戻る
- **外部連携の動作不確定**: 外部 API/サービスの動作確認が必要 → BDD へ戻る

### 差し戻し時の必須手順

1. 現工程の中断理由をユーザーに報告する
2. 差し戻し先と期待効果を説明する
3. ユーザーの明示的承認を得てから移行する
4. 差し戻し完了後の戻り先工程をユーザーと合意する

## 振り分け判断基準

- ユーザーが局所修正と明示しない限り、新機能は仕様整理から始める。
- 前工程の成果物がない場合は、assumption を明示した上でユーザーに確認してから進む。
- 作業が複数工程にまたがる場合は分解し、現在実行中の工程名を明示する。
- 実装を求められても API/DDD/契約が不足している場合は、コーディング前に不足 artifact を特定する。
- 作業は機能単位に保ち、複数機能を一括で設計・実装するバッチを避ける。

## 完了チェック（工程共通）

- 要件が シナリオ・API・UI 状態・テスト へ追跡できる
- DDD コンテキストと集約境界が API・DB 設計と矛盾していない
- 生成物（自動生成の OpenAPI 等）は手編集せず generated として管理している
- 長期に残るアーキテクチャ/技術決定に ADR が提案されている
- 先送りしたスコープは implementation note ではなく将来課題に記録している
