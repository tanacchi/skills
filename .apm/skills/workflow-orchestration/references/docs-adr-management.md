# ドキュメント・ADR 管理

## ドキュメント更新の判断基準

以下の変化が生じた場合、対応するドキュメントを更新する：

- **振る舞いの変更**: ユースケース・シナリオ・エラーパターンが変わった
- **インターフェースの変更**: API 仕様・コントラクト・型定義が変わった
- **コンテキスト境界の変更**: BC や集約の境界が変わった
- **非機能要件の変更**: パフォーマンス目標・セキュリティ方針が変わった
- **公開ワークフローの変更**: 開発プロセスや工程定義が変わった

変更がない場合は更新不要。変更の有無が不明な場合はユーザーに確認する。

## ドキュメント配置原則

- **プロジェクト固有の成果物**: プロジェクトの `docs/project/` 相当の場所に置く
- **再利用可能な手順・指示**: `docs/instructions/` 相当の共有領域に置く
- **長いドキュメントの複製禁止**: 要約して source へのリンクを貼る
- **要件 → 設計 → テスト のトレーサビリティ**: 各工程成果物間でリンクを維持する

## ADR 作成の判断基準

以下のいずれかに該当する場合、ADR の作成または更新を提案する：

- アーキテクチャパターンの選定（モノリス vs マイクロサービス等）
- 技術スタックの選定（フレームワーク・DB・ライブラリ等）
- データ/ストレージ戦略の決定
- API スタイルや通信パターンの決定
- ホスティング・インフラ方針の決定
- 非機能要件への対応方針
- 長期にわたるチーム横断ルール
- 過去の ADR を覆す新たな決定

## ADR 管理ルール

### ステータスルール

| ステータス | 意味 | 変更権限 |
|-----------|------|----------|
| Proposed | 提案中・レビュー待ち | 作成者 |
| Accepted | 承認済み・有効 | ユーザー（承認者）のみ |
| Deprecated | 非推奨・段階的廃止予定 | ユーザー（承認者）のみ |
| Superseded | 他 ADR により置き換え済み | ユーザー（承認者）のみ |

- 新規 ADR は必ず `Proposed` で作成し、ユーザー承認後に `Accepted` に変更する
- 作成者が直接 `Accepted` にしてはならない
- 一度作成した ADR は削除せず、ステータス変更で管理する
- 現在の作業が `Accepted` ADR と矛盾する場合、黙って上書きせず superseding ADR を提案する

### ファイル命名規則

- ADR ファイル: `[4桁連番]-[英語の短い slug].md`（例: `0001-monolith-architecture.md`）
- インデックス: `README.md`（ADR 一覧とステータスを記載）
- ADR 追加・ステータス変更時は必ずインデックスを更新する

### ADR フォーマット（最小構成）

```markdown
# ADR-[番号]: [決定内容の簡潔な説明]

## Status
[Proposed | Accepted | Deprecated | Superseded by ADR-XXXX]

## Context
[決定が必要になった背景・問題]

## Decision
[採用した解決策の詳細と理由]

### Alternatives Considered
| 選択肢 | メリット | デメリット | 評価 |
|--------|----------|------------|------|

## Consequences
### Positive
### Negative
### Risks and Mitigation
```

## 将来課題の管理

- 実在するが今回スコープ外の要求は将来課題に移す
- 現在のストーリーに必要な未完了 acceptance criteria を将来課題に隠さない
- 不確実な内容は project fact ではなく open question として記録する

## 安全ルール

- secrets・tokens・マシン固有の絶対パスを追加しない
- 採用判断が文書化されていない限り、tmp ファイルを source of truth にしない
